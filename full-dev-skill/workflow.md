# AI 全栈开发执行手册

版本：v1.1
适用：全栈等价对待，不预设前端或后端优先，按变更类型选择信息注入方式。
目标：让 AI 持续产出可靠成果。流程是手段，不为流程而流程。

---

## 0. 总原则

1. **全栈等价**：前端视觉/交互密集变更走后端无关的注入路径；数据模型/接口契约/业务规则密集变更走规范驱动路径。两者并行，无主次。
2. **流程服务于可靠性**：任何步骤若对“AI 产出可靠成果”无实际贡献，简化或跳过；若反复拦住同类错误，固化。流程每次修改的判据只有一个——AI 输出是否更可靠、返工是否更少。
3. **代码与提交差异是最终依据**：文档可能滞后，代码和 diff 是唯一真相。文档允许被重构，重构后必须与代码现状一致。
4. **知识库简洁**：AI 使用的知识以说明 + 文件索引为主，避免庞大繁琐。
5. **面向人的知识有结论、有逻辑、可路由**：结论先行，文件路由便于定位，支持链接跳转。

## 1. 场景—输入策略

| 场景 | 规范层 | 设计信息注入 | 后端信息注入 |
|---|---|---|---|
| 现有系统加模块 / Axure 原型 | OpenSpec `propose` | Axure RP MCP + 读取现有组件与令牌 | 读取现有接口定义与数据模型 |
| 加字段 / 小改动 / 截图 | OpenSpec `propose`（轻量） | componentize MCP + 现有组件对照 | 字段影响面：模型、接口、迁移、消费方 |
| 复杂模块 / Figma 设计稿 | Spec Kit 全流程 | Figma MCP | 接口契约 + 数据模型先行确认 |
| 新项目启动 | Spec Kit 全流程 | Figma / Axure MCP | 契约与模型设计先行 |

**交互与业务规则必须文字显式给出**：hover、点击、loading、禁用、成功、失败、空状态、权限、校验、分页、排序、默认值。静态图不可推断。

## 2. 执行阶段

### 阶段 0：项目基座（一次性，持续维护）
- 工具：Claude Code
- 动作：维护 `CLAUDE.md`（组件库、设计令牌、目录约定、接口契约规范、数据模型约定、迁移脚本规则、Skill 索引）与 `KNOWLEDGE.md`（知识索引，见第六节）
- 检查点：新会话能正确引用基座中的组件名、令牌名、契约格式

### 阶段 1：意图结构化 + 门禁（不可跳过）
- 工具：按场景选 MCP；存量用 OpenSpec `propose`，新项目/复杂模块用 Spec Kit `Specify → Plan → Tasks`
- 产出「实现范围说明」，必须包含：
  1. 复用哪些现有组件 / 接口 / 工具函数
  2. 新增哪些文件（前端组件、路由、后端接口、数据模型、迁移脚本）
  3. 交互状态与业务规则清单
  4. **接口契约**（请求/响应格式、字段类型、错误码）
  5. **数据模型变更**（字段、索引、迁移方向、回滚方案）
  6. 受影响消费方清单（哪些页面/服务/任务依赖该字段或接口）

#### 接口契约确认检查表（后端把关点）
- [ ] 请求/响应字段名、类型、必填性与现有规范一致
- [ ] 错误码与错误结构符合项目约定
- [ ] 分页/排序/过滤参数格式统一
- [ ] 字段变更是否破坏现有消费方（兼容策略：新增可选 / 版本化 / 迁移）
- [ ] 数据模型变更是否有迁移脚本与回滚方案
- [ ] 前后端字段命名与语义对齐，无隐式转换

**门禁：范围说明与检查表人工确认后才进入阶段 2。** 纯样式微调可轻量跳过，但凡涉及接口契约、数据模型、跨端字段、复用边界，必做。

### 阶段 2：全栈代码生成
- 工具：Claude Code + 主执行层（存量默认 Compound Engineering；新项目/复杂模块用 Superpowers 的 TDD）
- 约束：不得偏离阶段 1 范围；不得新建同类组件；样式引用令牌；**后端数据模型、契约、迁移不得由 AI 在执行阶段自行决定**，变更须回阶段 1 确认
- 产出：可运行的全栈变更

### 阶段 3：运行验证与反馈迭代
- 工具：`/run`、`/verify`、`/debug`
- 规则：**每轮反馈只聚焦一类问题**（先功能、再样式、最后边界状态）；出现“修 A 坏 B”时强制单类问题模式
- 标准：以实际运行结果为准，不以“代码看起来对”为准

### 阶段 4：质量门禁
- 工具：`ce-code-review` / Superpowers review / `/code-review`
- 检查：组件复用、令牌硬编码、契约一致性、交互状态完整性、意外变更、迁移脚本安全性

### 阶段 5：沉淀与迭代（核心）
- **代码与 diff 优先**：沉淀前先看本轮提交差异，以 diff 为事实基准，文档描述与之对齐
- Skill 固化：同类页面/变更 ≥2 次或同类错误 ≥2 次 → 写入 `SKILLS/`
- `CLAUDE.md` 回写：新组件模式、令牌、契约约定
- Compound 沉淀：`ce-compound` 记录有效调试路径、契约模式、踩坑
- 知识沉淀：按第六节写入知识库
- 流程版本递增：沉淀改变了执行步骤时

## 3. 按效果触发的迭代机制

| 机制 | 触发条件 |
|---|---|
| 阶段 1 门禁 | 涉及契约、模型、跨端字段、复用边界时必做 |
| 单轮单类问题 | 出现“修 A 坏 B”时 |
| Skill 固化 | 同类出现 ≥2 次，或同类错误 ≥2 次 |
| CLAUDE.md 回写 | 引入新组件模式/令牌/跨端约定 |
| Compound 沉淀 | 出现值得复用的调试路径、契约模式、踩坑 |
| 知识库更新 | 本轮产生可定位的结论、决策或影响面信息 |
| 流程版本递增 | 沉淀条目改变执行步骤 |
