这是一套可重复、可验收、可迭代的 Skill 生产操作指南，结构为：**原则 → 设计模型 → 生产步骤 → 质量校验 → 迭代机制**。

## 一、原则（第一性依据）

以下七条原则是后面所有步骤的判断依据，每一步的选择都要能回溯到这些原则。

| #    | 原则           | 含义                                                         | 违反后果                         |
| :--- | :------------- | :----------------------------------------------------------- | :------------------------------- |
| P1   | **确定性下沉** | 规则固定、需逐字节确定性的操作放 `scripts/`，不交给模型每次现场生成 | 输出漂移、不可复现               |
| P2   | **单职责边界** | 一个 Skill 只负责一个可独立验收的产出物                      | 职责纠缠、触发失准、难迭代       |
| P3   | **门禁可检查** | 门禁必须是可验证的条件（文件存在、字段非空、脚本通过），不是“建议” | 门禁形同虚设                     |
| P4   | **上下文经济** | `SKILL.md` body 精简，细节放 `references/`，按需加载         | 上下文膨胀、成本上升、注意力分散 |
| P5   | **触发可判别** | `description` 必须写清“何时用 + 何时不用”，两者缺一不可      | 该触发时不触发，不该触发时误触发 |
| P6   | **制品前置**   | 设计阶段产出结构化制品（文档/SQL/配置/任务），实现阶段受控落实 | 实现阶段返工、AI 多轮修改漂移    |
| P7   | **权限最小化** | `allowed-tools` 按阶段白名单，设计阶段不给写权限             | 阶段越界、门禁绕过               |

**可复用的 Skill 编写原则**：

| 原则                                                         | 体现在哪个 Skill       |
| :----------------------------------------------------------- | :--------------------- |
| **编写时遵循 Agent Skills 开放标准，不绑定单一运行时**；文件结构使用 `SKILL.md + references/` 通用格式 | 全部                   |
| **环境探测先于决策**；推荐必须附版本兼容性说明，标记为“建议”而非事实 | `env-probe`            |
| **自检清单必须是可逐项核对的**，而不是模糊的“检查质量”       | `implement` Step 3     |
| **简单模式的准入条件是“需求明确 + 改动机制清晰”**，文件数量不是唯一判据 | `SKILL.md` 模式判断    |
| **交互分级是设计 Skill 的核心机制**；门禁不是“建议”，而是可被编排层检查的**硬条件**；模式判断结果必须**文档化且可覆盖** | `design` + `implement` |
| **副作用操作必须用户确认**；沉淀不应阻塞主流程               | `knowledge-sink`       |
| **交付物是可直接放入 `.claude/skills/` 的结构**，每个 Skill 单职责、描述含触发与禁止条件 | 全部                   |

## 二、整体设计：Skill 四层结构模型

任何 Skill 都由四层构成，生产时逐层填充：

| 层         | 载体                                                  | 任务性质                            | 判断标准                                                     | 回答什么                               | 对应原则 |
| :--------- | :---------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------ | :------------------------------------- | :------- |
| **接口层** | frontmatter：`name` / `description` / `allowed-tools` | 触发条件；调用边界                  | 符合条件才加载；可用工具清单                                 | 何时被触发、能调什么工具               | P5, P7   |
| **指令层** | `SKILL.md` body                                       | 需要判断、解释、权衡                | 没有唯一正确答案，需要模型根据上下文决策（设计决策、交互分级） | 按什么步骤做、门禁是什么、输出什么格式 | P3, P4   |
| **资源层** | `references/` + `assets/`                             | 按需加载的详细规范;可复用的静态结构 | 篇幅长、只在特定步骤需要（测试策略、编码规范）;模板、schema、配置清单格式 | 需要时加载的详细规范与模板             | P4, P6   |
| **执行层** | `scripts/`                                            | 规则固定、需要逐字节确定性          | 模型每次生成可能漂移，但规则本身不变（SQL lint、命名校验、schema 检查） | 哪些确定性操作交给程序                 | P1       |

**Skill 谱系**（决定生产粒度）：

| 类型       | 职责                         | 例子                          |
| :--------- | :--------------------------- | :---------------------------- |
| 原子 Skill | 单一确定性操作或单一判断     | `env-probe`、`knowledge-sink` |
| 阶段 Skill | 一个流程阶段的完整产出       | `design`、`implement`         |
| 编排 Skill | 串起阶段、执行门禁、判断模式 | `dev-workflow`                |

## 三、生产步骤（SOP）

每一步都有输入、动作、输出、验收标准。按顺序执行，不跳步。

### Step 0：场景建模

- **输入**：一个真实工作场景（如“初级程序员用 AI 完成完整需求”）
- **动作**：画完整流程图，标出每个**人必须做判断或确认**的节点
- **输出**：流程图 + 判断点清单
- **验收**：每个判断点都能回答“人在这里确认什么”

### Step 1：边界切分

- **输入**：流程图 + 判断点清单
- **动作**：按 P2 单职责原则，把流程切成若干阶段；每个阶段对应一个“可独立验收的产出物”
- **输出**：Skill 清单（原子/阶段/编排）
- **验收**：每个 Skill 能用一句话说清“输入什么、输出什么、负责一个什么产出物”

### Step 2：组件选型

- **输入**：Skill 清单
- **动作**：对每个 Skill 的每项内容，按下表判定归属
- **输出**：每个 Skill 的四层组件清单
- **验收**：不存在“规则固定却放在指令层”或“需要判断却写成脚本”的错配

| 内容性质                       | 归属              | 判据（回溯原则） |
| :----------------------------- | :---------------- | :--------------- |
| 规则固定、需确定性、可独立运行 | `scripts/`        | P1               |
| 篇幅长、只在特定步骤需要       | `references/`     | P4               |
| 可复用静态结构（模板/schema）  | `assets/`         | P4, P6           |
| 需要判断、解释、权衡           | `SKILL.md` 指令层 | 无唯一答案       |
| 阶段权限约束                   | `allowed-tools`   | P7               |

### Step 3：接口定义

- **输入**：组件清单
- **动作**：写 frontmatter
  - `name`：短横线、动词或名词短语
  - `description`：**必须包含**“做什么 + 何时触发 + 何时不用”
  - `allowed-tools`：按 P7 白名单，设计类 Skill 不给 `Write`/`Bash` 写权限
- **输出**：每个 Skill 的 frontmatter
- **验收**：用 3 个正例 + 2 个反例测试 description，触发判断正确

### Step 4：指令编写

- **输入**：frontmatter + 组件清单
- **动作**：写 `SKILL.md` body，按固定骨架：
  1. 原则/理念（一段话）
  2. 步骤（编号，每步有明确动作）
  3. 门禁（按 P3 写成可检查条件）
  4. 输出格式（结构化，可验收）
  5. 禁止事项（明确不做什么）
- **输出**：`SKILL.md` body
- **验收**：body 不含“尽量”“注意”等模糊词；每条门禁都能被编排层检查

### Step 5：资源填充

- **输入**：`references/` 和 `assets/` 清单
- **动作**：逐个写出完整内容，模板必须可直接使用，不留占位符以外的空白
- **输出**：完整资源文件
- **验收**：模板类文件复制后填占位符即可用；参考类文件可独立阅读

### Step 6：脚本实现

- **输入**：`scripts/` 清单
- **动作**：写可独立运行的脚本，带用法注释、退出码约定、`set -euo pipefail`
- **输出**：可执行脚本
- **验收**：脚本脱离 Agent 可独立运行；退出码语义明确（0 通过 / 1 问题 / 2 参数错误）

### Step 7：门禁落地

- **输入**：所有 Skill
- **动作**：把每个门禁从“文字描述”转为“可检查条件”，写入编排 Skill：
  - 文件存在性检查
  - 字段非空检查
  - 脚本退出码检查
  - 用户确认状态检查
- **输出**：编排 Skill 中的门禁清单
- **验收**：故意跳过某门禁，编排层能拦住并报错

### Step 8：组装与验证

- **输入**：全部 Skill
- **动作**：放入 `.claude/skills/`，跑真实场景
- **输出**：执行 trace
- **验收**：见第四部分质量校验清单

## 四、质量校验清单

生产完成后，逐项验收。任一项不过，回到对应步骤修正。

| #    | 校验项     | 方法                                            | 对应原则 |
| :--- | :--------- | :---------------------------------------------- | :------- |
| 1    | 触发准确   | 3 正例触发、2 反例不触发                        | P5       |
| 2    | 单职责     | 每个 Skill 能用一句话说清产出物                 | P2       |
| 3    | 门禁有效   | 故意跳过门禁，被拦住                            | P3       |
| 4    | 脚本独立   | 脱离 Agent 可运行，退出码正确                   | P1       |
| 5    | 上下文精简 | `SKILL.md` body 不超必要篇幅，细节在 references | P4       |
| 6    | 制品完整   | 设计阶段产出文档+SQL+配置+任务拆分              | P6       |
| 7    | 权限最小   | 设计 Skill 无写权限，实现 Skill 白名单受限      | P7       |
| 8    | 模板可用   | 复制模板填占位符即可用                          | P4, P6   |

## 五、迭代机制

| 信号                 | 诊断                     | 修正位置                         |
| :------------------- | :----------------------- | :------------------------------- |
| 该触发没触发         | description 缺触发条件   | Step 3 补 description            |
| 误触发               | description 缺禁止条件   | Step 3 补“不适用于”              |
| 实现阶段被迫返工设计 | 设计制品清单缺项         | Step 2 补组件，Step 5 补模板     |
| 门禁被绕过           | 门禁不可检查             | Step 7 转为可检查条件            |
| 脚本输出漂移         | 本该下沉的规则留在指令层 | Step 2 重新判归属，Step 6 写脚本 |
| 上下文膨胀           | 细节错放 `SKILL.md`      | Step 2 移入 `references/`        |

### 迭代方法

1. **迭代原则**：每次只改一个 Skill 的一个组件，改完跑同一场景验证，避免多变量同时变更导致无法归因。
2. **跑一个真实的小改动**，观察 `env-probe` 是否漏探测、`design` 的待确认列表是否混入了本应阻塞的问题、观察 `implement` 是否在 `lint-sql.sh` 失败时**停止并修正**，而不是绕过脚本继续写。
3. **跑一个完整需求**，观察 `implement` 是否在必要条件缺失时正确停止，审查是否输出证据而非主观判断。
4. **读 Claude Code 的执行 trace**，找到“偏航”或“跳过门禁”的位置，把纠正写入对应 Skill 的 gotchas 或门禁规则中。
5. **不要往 Skill 里塞 Claude 已经知道的东西**——只写项目特定约定、非显然的流程和门禁规则，保持 `SKILL.md` body 精简，细节放 `references/`。
6. **不要把 `SKILL.md` 当成唯一载体**；能用脚本锁死的确定性，不要留给模型每次现场判断。

------

这套 Skill 的设计核心是：**把“重设计”落到门禁和文档上，把“交互分级”落到阻塞/非阻塞的判断上，把“简单/完整模式”落到自动判断且文档化的规则上，把环境确认落到独立的只读探测 Skill 上。** 全部结构遵循 Agent Skills 标准，可放入 `.claude/skills/` 直接使用，也可以迁移到其他支持该标准的 Agent 环境。

## 六、方法论一句话总结

**Skill 生产方法论 = 七条原则定判断依据 + 四层结构定组件归属 + 八步 SOP 定生产顺序 + 八项校验定验收标准 + 单变量迭代定改进方式。** 它保证同一个场景由不同人执行，产出的 Skill 结构一致、门禁一致、可验收标准一致，这是“可重复稳定生产”的含义。
