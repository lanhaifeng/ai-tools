# 开发工作流编排器

## 设计理念：重心前移，受控实现

- 设计阶段的目标是**消除实现阶段的不确定性**：能提前确定的接口、SQL、配置、迁移方案，全部在设计阶段产出草稿。
- 实现阶段**不接受“先写写看，再改改”**：每个 Task 的输入是已确认的设计制品，执行是确定性的落实，不是探索。
- 简单模式仍然需要设计确认，只是确认的粒度和交互轮次更少。

## 模式判断

| 条件 | 模式 | 设计阶段强度 |
|---|---|---|
| 需求明确；改动机制清晰（如加字段、改展示） | 简单模式 | 一句话方案 + 影响文件清单 + 必要的 SQL/配置草稿确认 |
| 新功能、多模块、涉及 SQL/配置/迁移、验收标准不明确 | 完整模式 | 完整设计文档 + SQL 脚本草稿 + 配置清单 + 任务拆分 |
| 无法判断 | 完整模式（待确认） | 同上，模式标记写入文档 |

## 全流程

### Phase 0 — 环境探测（`env-probe`，只读）

调用 `scripts/detect-test-frameworks.sh` 确定性探测，模型只读取摘要，不猜测。

### Phase 1 — 设计（`design`，重心所在）

产出**技术制品清单**（至少包含，按需裁剪）：
1. 设计文档（`references/design-doc-template.md`）
2. **SQL 脚本草稿**（DDL / DML / 迁移脚本，使用 `assets/sql-migration-template.sql`，由 `scripts/lint-sql.sh` 校验）
3. **配置项变更清单**（使用 `assets/config-change-manifest.md`，明确环境变量/配置键/默认值/是否敏感）
4. 任务拆分（每个 Task 标注依赖的设计制品）

**设计门禁**：阻塞性问题必须回答；非阻塞问题写入待确认列表，用户一次性确认。**未经确认的设计制品，不进入实现。**

### Phase 2 — 实现（`implement`，受控）

按 Task 逐个实现。每个 Task 完成后：
1. 自检（语法/需求/逻辑/规范/优雅）
2. 运行 `scripts/lint-sql.sh` 和 `scripts/validate-config-schema.sh`（如涉及 SQL/配置）
3. 完整模式下触发独立审查
4. 必要条件缺失时停止该 Task；可后补条件缺失时继续并记录待办

### Phase 3 — 知识沉淀（可选，完成后询问）
